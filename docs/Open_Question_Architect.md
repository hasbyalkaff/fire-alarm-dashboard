### Feeder Integration Boundary

For Version 1, the system will use **PostgreSQL as both the source of truth and the real-time event signaling mechanism**, without Redis.

The integration flow will be:

```text
Modbus Feeder
    │
    ├── Update current device/panel state
    ├── Insert event history
    └── PostgreSQL NOTIFY on channel `facp_events`
                │
                ▼
Dashboard Backend
    ├── LISTEN to `facp_events`
    ├── Fetch full event data from PostgreSQL
    └── Relay updates to connected browsers through SSE
```

The Feeder must publish a PostgreSQL notification after successfully committing the related database transaction. The notification payload should remain small and contain only the event type and event identifier, for example:

```json
{
  "event": "alarm.created",
  "event_id": "evt-123"
}
```

PostgreSQL remains the permanent source of truth for current state and event history. `LISTEN/NOTIFY` is used only as a real-time signal and is not treated as a durable message queue.

If the Dashboard Backend temporarily loses its database listener connection, it must perform a reconciliation process after reconnecting by querying events created after its last successfully processed event.

This approach is selected for Version 1 to keep the architecture simple, reduce infrastructure dependencies, and avoid unnecessary operational complexity. Redis or another message broker may be introduced later if event volume, consumer count, or delivery requirements increase.


### Database Access Boundary

The Dashboard Backend must not have write access to Feeder-managed or hardware-backed domain data.

A dedicated PostgreSQL role, such as `dashboard_ro`, will be created with `SELECT`-only permissions on domain tables including:

* panel status
* device current state
* alarm events
* fault events
* event history
* Modbus mapping data

The Dashboard Backend may use a separate application schema for data that belongs to the dashboard application itself, such as:

* users
* roles
* permissions
* application settings
* authentication sessions
* audit logs

The dashboard application may write only to its own application schema. It must not insert, update, or delete data generated by the Modbus Feeder.

This restriction must be enforced at the PostgreSQL permission level, not only through application code, to ensure that the monitoring application cannot modify hardware-backed fire alarm data.
